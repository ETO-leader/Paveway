## 0. 一页摘要



### 0.1 项目是什么

这是一个**以现有 Coding Agent 为运行主体、专门面向 OI 学习的 AI 教练**：根据用户提供的训练目标、题目、日程和历史表现，协助安排当天训练，适时追踪进度、调整计划，并分析做题与模拟赛表现。它不应只做计时和催促，还需要能够理解“看过题解、只口胡、真正独立写出并 AC”等不同学习状态，从而给出有价值的建议。

原始表述从“搞个 OI 监督训练和分析的 agent”，收敛到“基础功能就是安排和分析”。[原始 L5326–L5326，L6597–L6618]

项目后续希望可以挂载更专业的 OI Skill，包括人话题解、寻找人类能够追踪的思考路径、Manim 动画和造题，也可能探索跨题目的深刻 insight。这些是可扩展能力，并非都要塞入初版核心。[原始 L64–L128，L199–L214]

### 0.2 到记录结束时最接近共识的总体架构

```text
用户
  │
  ▼
现有 Coding Agent（初期偏向 OMP；也希望支持 Codex 等）
  │
  ├─ OI 教练核心 Skill / 模块化系统说明
  │    ├─ 训练安排、跟进、训练效果分析
  │    ├─ 可配置的用户偏好 / 外部约束
  │    └─ 按需使用独立扩展 Skill
  │
  ├─ 原生工具（文件、终端、一般网络访问等）
  │
  ├─ Tijian MCP（题库、题面、做题状态等 OI 业务能力）
  │    └─ Tijian 本地存储与已有抓取能力
  │
  ├─ 其他用户自行添加的 MCP / 工具
  │
  └─ 独立唤醒启动器（由教练项目一侧实现）
       ├─ 用户可配置的 Agent 启动命令 / 适配层
       ├─ 待执行唤醒事件队列
       └─ 单实例执行、锁和超时事件处理

长期记忆与历史会话检索：优先评估现有 Agent/插件能力，独立于 Tijian 业务接口。
跨设备同步：讨论过 Git + 自定义 remote，尚未确定同步范围和冲突策略。
```

**关键边界**：教练项目是独立于 Tijian 的项目，借助 Tijian MCP 获取业务数据；不再以“在 Tijian 内开发通用插件 / 自造完整 Agent Harness”为初版路线。Tijian MCP 文档与教练 Skill 应解耦，MCP 接口变化时尽量只更换独立接口说明。[原始 L1775–L1811，L1901–L1910，L2281–L2296，L3151–L3229]

**自动唤醒后来的结论**：不由 Tijian 负责；教练项目一侧实现可配置 Agent 启动命令、锁与待执行请求队列。[原始 L528–L564，L1859–L1880，L2176–L2227]

### 0.3 不应误认为已经定案的事情

- 每天一个对话、每个任务一个对话、唤醒时继承原对话、自动新开对话——**有讨论，没有统一的最终规则**。[原始 L973–L1051，L1330–L1375]
- 三层记忆的**概念**较清晰，具体实现方式、检索插件及跨设备同步**尚未定案**。[原始 L619–L713，L763–L848，L1057–L1103]
- Tijian 内置时间管理或任务队列曾被讨论，但与独立项目的**唤醒队列**不是一回事；两者的业务边界仍有待确认。[原始 L52–L52，L3223–L3229]
- 比赛排行榜、学校 OJ、自动推荐好题、造题、视频、深刻洞察都是有价值的功能方向，但**初版范围没有逐项锁定**。[原始 L64–L70，L2254–L2257，L3578–L3638]

## 1. 目标、价值与使用场景

### 1.1 核心目标

1. **训练安排**：用户提供当日 TODO、可用时间、休息安排等；Agent 分配题目顺序、预估耗时、何时考虑看题解以及何时需要检查进度。
2. **过程监督与动态改计划**：计划不是一份生成后不再变化的表格。用户可能提前完成、超时、卡题、临时休息、只口胡或不写代码；Agent 据实修订后续计划。
3. **学习效果分析**：结合题目、题解使用情况、做题过程、模拟赛成绩与做题状态，分析掌握程度、薄弱点和训练价值，给出后续重点。
4. **尊重 OI 学习规律**：题目数量或 AC 数不是唯一指标；有价值的深度思考、口胡、题解复盘和实际编码都应区别记录。
5. **允许用户自行调整**：训练时间、休息时间、外部约束、偏好、可用模型与辅助 Skill 不应被写死。

证据：[原始 L5163–L5248，L5326–L5326，L6542–L6618]

### 1.2 典型使用流程（根据聊天内容重组的示例，非最终 UI 规格）

**早上或当天首次启动**：用户输入「今天要做 A、B、C，12:00–14:00 休息」。Agent 结合用户情况，为每道题估时，生成训练与休息相间的日程，并安排下一次检查节点。[原始 L5193–L5248]

**做题过程中**：到节点触发 Agent 检查。用户可以反馈「还没想到关键性质」「已经口胡出来但没写」「刚才摸鱼五分钟」「我想再想十分钟」「已经看了题解」。Agent 决定是否延长思考、提供 hint、建议看题解或调整后续任务。[原始 L4935–L4959，L5130–L5169]

**模拟赛或一天结束后**：根据题目和结果，分析哪些不会、哪些虽然 AC 但方法或理解不足、哪些属于值得复盘的题，再决定后续加强方向。晚间调用曾被提出，但并未锁定为固定时刻的强制工作流。[原始 L5181–L5184，L6573–L6588，L3590–L3605]

**第二天继续未完成的难题**：希望能够找回昨日的任务状态及关键推理，而不必从头重新叙述；究竟通过原会话恢复还是记忆/历史检索实现仍未定。[原始 L973–L1009]

### 1.3 产品定位

- **OI 特化，不重新发明通用 Agent**：终端、代码、网络和普通工具尽量复用 Coding Agent，项目集中在 OI 业务知识和教练工作流。[原始 L964–L970，L3151–L3229]
- **长期可维护**：不仅服务两位发起者；曾表达希望项目能长期存活、后人接手的愿望。[原始 L4233–L4267]
- **以学习质量优先**：避免把外部数量指标当成真实能力，分析报告应能帮助选手理解自身水平。[原始 L3969–L3978，L5070–L5088]

## 3. 与 Tijian 的关系和责任分工

### 3.1 最后选择：独立项目 + Tijian MCP

讨论经历了“做在 Tijian 里 / 插件 / 独立项目 / 自造 Agent Harness”等方案，但后来明确偏向：

- OI 教练 **独立成项目**，主要交付 Skill、配置和一小部分必需的程序基础设施。
- **现有 Coding Agent 是运行主体**；Tijian 不需要重新实现一个通用 AI Harness。
- **Tijian 通过 MCP 提供 OI 数据和业务操作**，核心教练提示词不直接耦合 Tijian 的内部实现。
- Tijian 不负责执行 Agent 唤醒；独立项目一侧提供一个**启动器/外壳**。

[原始 L1778–L1811，L1859–L1910，L2281–L2296，L3151–L3229，L528–L564]

### 3.2 对话明确提及的分工

| 责任区域                              | 记录中的归属             | 备注                                 |
| ------------------------------------- | ------------------------ | ------------------------------------ |
| Tijian MCP 及其接口说明文档           | **Tijian 一侧**          | 有明确“我负责 Tijian MCP 以及其文档” |
| 教练 Skill 的研发和维护               | **朋友/教练项目一侧**    | 有明确“你负责 Skill”                 |
| 跨 Agent 的唤醒启动器、可配置命令、锁 | **教练项目一侧**         | 后续明确 Tijian 不负责唤醒           |
| Tijian 的题库、业务数据、原有爬取能力 | **Tijian 一侧**          | 由 MCP 暴露，而非让教练直接改数据库  |
| 第三方/用户安装的其他 MCP 和 Skill    | **由用户或外部生态提供** | 核心项目尽量复用，不重复维护         |

### 3.3 业务协议文档与教练 Skill 必须正交

记录中有非常明确的升级目标：**Tijian 改 MCP 接口时，替换一份 `tijian mcp.md` 类的独立说明即可，其他 Skill 不应到处修改**。[原始 L2281–L2296]

这一目标至少要求逻辑上拆开三种东西：

1. **MCP 业务说明**：有哪些接口、参数、返回值、错误、业务语义以及可用版本（由 Tijian 一侧维护）。
2. **教练策略**：如何安排任务、分析做题、设置唤醒、解释状态（由教练项目维护）。
3. **Agent 平台适配**：如何加载 Skill、连接 MCP、恢复会话、调用终端（按平台处理）。

后两项不应内嵌 Tijian API 名称和参数。这是对对话共识的结构化表述，并非已敲定文件树。

同时，**不强制长期兼容所有旧版本 MCP**：当时明确认为接口有可能随大版本变化，只要提供更新后的文档并改适配即可，开发者不必承诺 v1.0 永远不变。[原始 L3662–L3698]

### 3.4 Tijian 数据获取优先级

对“要一题题面”的较后期方案非常清楚：

```text
优先：读取 Tijian 已存的本地题面
  └─ 如果没有：调用 Tijian MCP 让 Tijian 抓取并存储
       └─ 如果仍失败：允许 Coding Agent 自己尝试访问网站
```

一般网络访问（无 Tijian 专门业务语义）尽量使用 Agent 本身提供的能力，而非把整个通用网络代理/浏览器都做进 Tijian MCP。[原始 L3032–L3092]

这体现的不是“禁止一切上网”，而是**已有可信业务数据优先，失败有降级路径**。对话强调的初衷是减少重复爬取、提高题面一致性；其正确性保障仍依赖 Tijian 数据质量。[原始 L4585–L4588，L3062–L3068]

### 3.5 Tijian 当前能力与接口缺口（截至聊天时的口述）

**已有或被描述为已有**：OJ 题面爬取及本地缓存、在线补抓、做题状态 emoji、命令行使用的可能性；但这些只是聊天中的描述，本文未独立检查 Tijian 代码。[原始 L2451–L2460，L4503–L4561，L5136–L5151]

**明确缺口或尚未确认**：定时提醒当时未实现；比赛后端/排行榜接口当时还没修好或不开放；MCP 首版不能假定覆盖所有业务；学校 OJ 接入仍是扩展讨论。[原始 L2227，L2254，L3590–L3638，L4124–L4175]

因此，**教练首版只依赖 Tijian 已稳定提供的最小接口**是讨论方向，但最小接口列表并未在记录里最终敲定。

## 4. 训练安排、任务记录与进度分析

### 4.1 计划输入

对话中明确提及的输入包括：

- 当日 TODO / 指定要做的题目；
- 用户的作息、可用训练时间、强制休息时段；
- 当下进度反馈（开始、卡住、口胡完成、摸鱼、延长、看题解等）；
- 历史做题记录、模拟赛题目和成绩；
- 家长/教练提出的额外数量或汇报要求。

[原始 L5193–L5248，L5175–L5184，L3969–L3978]

### 4.2 计划输出及调整方式

讨论最自然的工作流是：

1. Agent 制订今日顺序与时间安排，估计各道题的工作时长；
2. 选定**下一次**需要检查的时间/计划节点；
3. 用户做题，期间随时可以插入反馈或主动请求调整；
4. 到节点时唤醒 Agent，分析当前是否完成、需不需要继续想、是否该看题解或换题；
5. 根据新的事实重排剩余计划。

[原始 L5193–L5248]

这里需要同时兼容“计时和休息”与“进入状态时不想被刚性时刻打断”的矛盾。有人指出精确到固定时刻可能过于僵硬；随后偏向“Agent 分配 + 可以调整”。[原始 L5471–L5492]

### 4.3 做题状态不是单个 AC 布尔值

对话专门涉及了以下区别：

- 没做 / 在思考；
- 只口胡，不写代码；
- 口胡后再写代码；
- 已看题解 / 未看题解；
- 已想到关键步骤、理解部分思路；
- 已编写代码及 AC 状态；
- 因外部要求完成的数量性任务，与真正掌握程度分别看待。

现有 Tijian 据称已有 emoji 做题状态；Agent 可以利用用户手工补充的自然语言解释来细化。[原始 L4503–L4512，L5031–L5088，L5130–L5169]

**不能推断已经存在上述全部结构化字段**。它们是对 Agent 所需区分的概念的抽取，具体应由 Tijian MCP 数据模型确认。

### 4.4 分析应该关注什么

聊天讨论的重点是：不仅判断“做出来没有”，还需考虑题目的训练价值、用户是否借助题解、是否掌握关键发现、模拟赛结果暴露的短板，以及下一步值得训练什么。[原始 L5178，L6573–L6600]

尚未决定：每次题目完成后是否立刻写总结、每日分析固定在晚上还是按需、模拟赛数据缺失时如何降级、如何计算长期能力指标。

### 4.5 外部要求与真实学习状态

聊天中希望将家长/教练的任务量要求做成**独立可配置约束**，不要污染面向学习的核心判断。引用的 GPT 回复建议一个类似 `external_requirements_prompt.md` 的独立模块，专门处理额外要求，并保留区分“口胡”“看过题解”“真正通过”的记录。[原始 L3969–L3978]

也出现了“为了应付要求让 Agent 代写/提交代码”的讨论，**没有形成作为正式产品功能的确认共识**；它与“真实能力记录”存在张力，不能在整理时偷偷变成既定功能。[原始 L5034–L5097]

## 5. 定时唤醒：独立启动器而不是 Tijian 职责

### 5.1 唤醒要解决的产品需求

唤醒不是单纯弹一条通知，而是让 Agent **重新检查做题进度和计划是否仍合理**，必要时提出问题、调整下一节点；这才是它和普通计时提醒的区别。[原始 L1384–L1393，L5205–L5229]

最初设想“Agent 写一个下次唤醒时间，到点自动启动 Agent”，一度认为可以让 Tijian 负责调命令。后续意识到跨 Coding Agent 兼容性和职责边界，逐步转向**由独立项目自己实现外壳**。[原始 L2098–L2146，L2185–L2227，L1778–L1880]

### 5.2 较后期收敛的机制

| 机制           | 聊天中形成的方向                                             | 仍未明确的细节                              |
| -------------- | ------------------------------------------------------------ | ------------------------------------------- |
| Agent 启动     | 将启动/发送封装成命令；由用户配置所用 Agent 命令，初期 OMP 优先 | 不同 Agent 的 resume/session 命令、参数协议 |
| 唤醒事件产生   | Agent 决定后续唤醒时间；曾举“写到 timeout.txt”等文件形式     | 文件格式、存储路径、时区及更新原子性        |
| 待执行事件     | 引入 queue 保存尚未执行的请求                                | 任务去重、修改、撤销、持久化机制            |
| 互斥           | 使用 `.lock` 等锁，确保前一轮还没结束时不重叠启动            | 进程崩溃后的锁回收、如何识别悬挂实例        |
| 执行顺序       | 唤醒处理倾向**串行**                                         | 多任务公平性、长任务阻塞策略                |
| 迟到事件       | 到期事件若在当前时间之前，讨论过立即启动                     | 大量积压时是否合并、过期丢弃、用户交互      |
| Agent 改写事件 | 希望 AI 有权移除或修改不合理的唤醒事件                       | 权限边界、日志审计、避免误删                |
| 定时起点       | 一度讨论前一 Agent/handler 完成后再计时                      | 对绝对时间与相对延时的语义尚未最终裁定      |

依据：[原始 L1615–L1684，L1727–L1754，L2170–L2188，L528–L564]

**需要防止的典型冲突**：Agent 预定一分钟后再唤醒，但它自己当次推理已经持续超过一分钟；这引出了锁、串行、完成与计时起点的讨论。[原始 L1736–L1754]

聊天还提出让 AI 处理“积压上百万个不合理事件”，甚至另起模型或 subagent 处理 MCP 通信。这是**探索性方案**，并没有取代基本的程序队列与锁，更不能被解读为已确定要用某个特定模型守护。[原始 L1603–L1633]

### 5.3 两个不要混淆的 queue

- **教练启动器的 wake queue**：技术上保存“何时、为何重新调用 Agent”，是自动唤醒的运行队列。[原始 L531–L543]
- **训练计划的 TODO / 训练安排 queue**：业务上保存待做题目、预估时间、休息和计划变动。[原始 L5242–L5248，L5462–L5471]

此外，文件开头出现了“**Tijian 内置任务队列需要支持什么**”这个最新问题，没有对应的后续完整回答。[原始 L52] 这很可能在讨论第三种 Tijian 业务任务队列，但**无法仅凭一句话确认它与前两者的关系、存储者和接口范围**。

### 5.4 跨不同 Coding Agent

对话中的目标是**不限于 OMP**：优先在 OMP 上做出可用版本，但希望换成 Codex 或其他可用命令行启动的 Agent 时，主要修改配置/适配层，而不是改 OI 教练策略。[原始 L2143–L2209]

“所有主流 Agent 都能恢复同一会话或支持无头执行”**没有在记录中得到验证**。在没有完成可用性测试之前，这只能是兼容性目标。

## 6. 上下文、长期记忆、历史会话与跨设备

### 6.1 讨论最终明确的三层概念

后期把数据分成类似存储层级的三部分：[原始 L619–L713，L1057–L1088]

| 层次                         | 在对话中的含义                           | 适合保存的东西                             | 地位                   |
| ---------------------------- | ---------------------------------------- | ------------------------------------------ | ---------------------- |
| **L1：当前对话上下文**       | 当前会话内直接可见的互动与推理           | 正在解决什么题、目前卡点、刚制定的训练计划 | 概念明确               |
| **L2：AI 可维护的记忆/笔记** | 从经历中提炼、可增改且可能有时间戳的摘要 | 用户长期偏好、能力画像、仍有效的任务要点   | 概念明确，格式未定     |
| **L3：历史对话库**           | 可回溯以前会话，按需通过检索工具读取     | 原始聊天、当时详细推理与被压缩掉的上下文   | 概念明确，检索机制未定 |

聊天一度尝试再分“重要/不重要的长期记忆”，并以“脑中的东西/笔记本里的东西”作类比；这是概念探索，不应武断认定已经有稳定的四层或多级缓存规格。[原始 L641–L686]

### 6.2 为什么不能无限增长单个上下文

有人指出：长上下文可能降低效果、增加 token 成本；但仅靠每天总结又容易丢掉过去某个任务的关键推理。故讨论过以下路径：

- 每日保留一个会话，第二天更新；
- 按任务而不是按日期分会话；
- 新会话注入最近对话片段和长期记忆；
- 允许 Agent 使用工具精确检索旧会话；
- 未完结的难题保留原会话或恢复足够多的历史。

[原始 L973–L1119，L1312–L1375]

**未最终决定**使用哪一种作为统一默认；“每次都附最近 100k 对话”是曾经提出又被质疑的信息保留方案，不能直接当配置要求。[原始 L1091–L1119]

### 6.3 倾向复用现成记忆及历史检索生态

较后期讨论明确不希望从头写完整记忆系统，想利用 OMP/其他 Agent 的自动记忆功能，以及能搜索旧聊天的插件或 MCP。[原始 L805–L824]

记录中提到了候选轮子 [`vshulcz/deja-vu`](https://github.com/vshulcz/deja-vu)，并讨论向量检索可能使用免费 embedding 服务；**只说明发现候选，没有实测兼容 OMP、效果或稳定性**。[原始 L751–L767，L839–L848]

因此“已有插件完全解决 L3”和“确定选用 deja-vu”都不是可据此下的结论。

### 6.4 跨设备同步

聊天把**Git + 用户自定义 remote**作为一个颇受认可的主意，设想把项目/记录放在可配置目录并提交推送。之后马上遇到“会话由各个 Agent 自己保存、跨设备恢复对话状态较复杂”的问题。[原始 L4998–L5028，L1134–L1158，L1276–L1288]

需要区分四类数据：训练数据、Skill 配置、可维护的长期记忆、Agent 会话历史。**哪几类必须通过 Git 同步、哪几类只需本地存储、如何处理同步冲突，都没确定。**

记录还讨论了跨平台：希望至少支持 Linux；手机端当时表示不支持。[原始 L4959–L4968]

## 7. Skill、提示词模块与可扩展性

### 7.1 模块化不是把所有能力塞进主提示词

较后期的思路是：教练核心本身可看作一个 Skill，但应区分**始终需要的基础说明**、**可选用户/领域 Skill**、**外部工具/MCP 的接口说明**。[原始 L137–L175，L262–L319]

讨论曾使用 `sys prompt` / `usr prompt` 这样的概念，后来又倾向将用户加载的能力直接称为 Skill。**名称不是最终的配置 schema**。[原始 L151–L175，L292–L298]

### 7.2 被明确点名的独立知识文档

| 模块                | 作用                                      | 最后讨论倾向                                 |
| ------------------- | ----------------------------------------- | -------------------------------------------- |
| 好题标准            | 帮 Agent 理解什么题值得训练、质量差在哪里 | 核心独立模块                                 |
| CNOI 介绍           | 解释中国 OI 体系、题型、竞赛语境          | 核心独立模块                                 |
| 近年 CNOI tasks     | 为竞赛体系提供近年实例                    | 起初单列，后倾向**并入 CNOI 介绍**           |
| Tijian MCP 使用方法 | 说明 Tijian 数据/接口如何使用             | **独立 MCP 文档**，由 Tijian 一侧维护        |
| 如何研究深刻洞察    | 指导高质量、可泛化 insight 的发现         | 有人提议，但明确担心“太空中楼阁”，未钦定必带 |
| 家长/教练额外要求   | 调整汇报和任务约束，而非改写核心学习标准  | 提议可选启用、独立配置                       |

依据：[原始 L214–L253，L585–L594，L3969–L3978]

### 7.3 可选扩展 Skill 列表

聊天结束时点名了四类：[原始 L64–L128]

1. **人话题解**：用可理解的解释替代生硬的形式推导；后来的共识是题解 Skill 太庞大，不内置在教练基础设施中。[原始 L238、L307]
2. **寻找人类思考路径**：对“已看题解仍觉得难以想到”的题，尝试给出可以从题意逐步发现关键转化的路线。[原始 L110–L119]
3. **Manim 动画**：把需要形象化的证明或算法做成动画。[原始 L67]
4. **造题**：作为高级训练功能。围绕 CNOI 题面风格、JOI 式训练价值和好题样本进行探索。[原始 L64、L2785–L2812]

另外有**深刻 insight 研究**方向，希望把特殊技巧上升到线性变换、矩阵行、可推广结构等本质理解。例如聊天用“固定采样点的多项式点值 → 线性函数/矩阵行点积”的例子说明什么叫能让原本陌生的招数变得自然的理解。[原始 L2514–L2529]

这不是已研发成功的算法，也不是所有题都能挖掘出此级别 insight 的保证。[原始 L199–L214、L2610–L2625]

### 7.4 规则的承载层

曾明确提到 OMP 环境里的 `RULES.md` 与 `AGENTS.md`，并建议把频繁被忽略的约束放在更强的注入位置，至于具体怎么集成尽量依靠 Agent 自己的机制。[原始 L268–L286]

这些属于聊天中对特定 Agent 的**经验性说法**；并未提供跨 Agent 的一致注入语义，也不能用它代替测试不同平台的 Skill 加载方式。

### 7.5 工具类型讨论的收敛

一度将工具分为：Coding Agent 原生工具、教练项目必需工具、用户自行增加的外部工具；后又讨论 `builtin toolcall / extension toolcall`。中途多次把“Skill、工具、MCP、文档”混为一谈，最后趋向“现成 Agent 自己管理 Skill，外部 MCP 可由用户安装”的思路。[原始 L307–L371，L471–L519]

**结论级别**：分层与可配置是稳定方向；**没有**确认需要实现一个允许用户任意上传可执行代码的自定义工具平台。[原始 L365–L465]

## 8. OI 领域知识、好题标准与题库

### 8.1 为什么要有“好题标准”

初期就担心 Agent 不懂题目质量，只会推荐低价值训练题；因此需要可参考的正负样本、稳定的评价标准及必要的人工审核。[原始 L6393–L6442]

讨论中分享过一份以**训练价值**为核心的 0–10 分尺度，既重视高质量思维发现，也考虑常用数据结构的深入理解、多解法和知识点是否过于偏门。[原始 L4428–L4445]

**量表摘要**（压缩表达，不替代原版全文）：

| 分数 | 原始评分说明的核心含义                 |
| ---- | -------------------------------------- |
| 0–2  | 基本缺乏训练价值，甚至不如正常板子练习 |
| 3    | 普通板子或质量不高                     |
| 4    | 在基础知识点上多一点有价值的变化       |
| 5    | 有不少训练价值，可以支撑稳定进步       |
| 6    | 较长思考链、观察与思维训练价值明显     |
| 7    | 神题，能显著提高高质量训练密度         |
| 8    | 非常神，常有不寻常的关键发现           |
| 9    | 极罕见的超级神题                       |
| 10   | 近乎保留给极端例外                     |

这是**某位讨论参与者提出的主观校准尺度**，不是通行竞赛标准，也不能仅靠分数就得到好的自动推荐结果。[原始 L4428–L4445]

### 8.2 聊天中的正负样本线索

- **曾被明确称为“好题”**：`P9470`。[原始 L6285–L6288]
- **曾被明确称为“烂题”**：`P10808`、`P14412`、`QOJ contest 3773 / problem 18412`、`CF 2271G`。[原始 L6262–L6329]
- **被作为较高分示例**：`CF1844G Tree Weights`、`P14342 [JOISC 2019] Naan`（原文质量 8）；`CF702F T-Shirts`、`P10104 异或图`（质量 7）。[原始 L4436–L4437]
- **对于 `Two Currencies` 与某些“板子/训练价值”的分歧**：讨论中有争议，**不视为已确定负样本**。[原始 L6333–L6351]

还曾计划积累至少 10 个具有迷惑性的负样本，即普通模型可能误认成好题、但训练价值不足的题。[原始 L6276–L6282，L6027–L6036]

### 8.3 推荐与批量分析的研究构想

讨论过先让 AI 给题库题目生成独立审查、题解与“核心技巧”标签，再做向量检索或蒸馏，以免用户找好题时只能依赖搜索引擎和模型记忆。不过成本、质量、覆盖率和现实收益都没验证，讨论最后认为**应先完成基础功能，再做小范围实验**。[原始 L2610–L2718]

也讨论过“CNOI 的形式、JOI 的训练价值”作为造题 Skill 的特色定位，以及从 JOI 近年题目中先让 AI 筛选、人工逐个确认的正样本工作流。这是造题/质量研究的上下文，**不代表教练只允许推荐 JOI**。[原始 L2751–L2812]

## 9. 平台、发布与项目工程边界

### 9.1 平台及运行形式

- **初始偏好 OMP**，因为支持命令行调用、用户自定义模型/配置；但希望适配其他 Coding Agent。[原始 L6173–L6179，L2143–L2209]
- **先 CLI、后 GUI**：讨论曾明确“先实现命令行，后期再加前端”。这在早期插件方案阶段提出；在转向独立 Agent 方案后仍符合轻量方向，但不能当成已确定的产品 UI 路线图。[原始 L3893–L3908]
- **Linux 至少应支持**；手机端曾表示不支持。[原始 L4959–L4968]
- **用户自己配置模型或 role**：有过讨论认为 OMP 已能完成模型角色配置，教练项目无需重复实现。[原始 L567–L573]
- **ChatGPT/云端使用**：可考虑没有后台定时唤醒的问答/分析子集，不应据此承诺平台兼容已完成。[原始 L1980–L2037]

### 9.2 开源与宣传

关于是否立即开源、在役是否公开宣传、是否只向熟人推广、退役后留给后人、长期是否维护等存在反复权衡。[原始 L4682–L4805]

倾向有：希望长期有价值；开发可用 GitHub 协作；部分谈话支持开源但不大规模宣传。**未形成可执行的发布许可、宣传时间或维护承诺**。

当时还担心 Tijian 中的 VJudge 相关爬取/提交实现可能带来法律或平台规则风险，并提出只开源可解耦部分等想法。这里应当作为**Tijian 依赖/发布风险**保留，而不是假设当前已经有被允许公开的代码或授权。[原始 L4333–L4369]

### 9.3 成本和资源

讨论涉及 Agent token 开销、模型能力、免费向量模型、小范围实验，以及“大规模为全部 OJ 题目预处理”可能花多少钱。**没有形成真实预算、单题硬成本上限或最终模型清单**。[原始 L751–L754，L2619–L2679，L4901–L4910]

其中“单题一块钱以内”是估算情境而非产品价格目标。[原始 L2646–L2664]

## 12. 可落实的最小范围（整理者建议，**非对话定案**）

> 本节不是新增“已确认需求”；仅把已讨论事项转成便于两位开发者下一步核对的**候选实施顺序**。如果追求严格的聊天摘要，可将本节移除而不影响前面的共识。

### Phase A：能完成一次真实训练日

- 基于一个已能命令行调用的 Agent，载入教练核心 Skill。
- 用户给出 TODO 和休息时段，得到可手动调整的计划。
- 从 Tijian MCP 读取**已确认可用**的题面和做题状态；MCP 失败可告知用户并降级。
- 用户能报告进度、口胡/看题解/代码通过等信息，Agent 修改后续计划。
- 至少形成一份当天训练结果分析；不要承诺自动荐题或全 OJ 自动处理。

### Phase B：闭环定时跟进

- 独立启动器按明确的时间语义启动 Agent。
- 可配置不同 Agent 命令，先保证一个 Agent 跑通。
- 唤醒事件持久化、串行、锁、防重入，用户和 Agent 可改动后续事件。
- 用“前次会话尚未结束”和“错过多个唤醒”的场景验证运行语义。

### Phase C：长期学习与扩展

- 实验现成自动记忆与历史会话检索组件，而不是提前重写数据库。
- 验证跨设备时什么信息能真正续上，保留未完结题目的必要过程。
- 单独接入题解、思考路径、Manim、造题等 Skill；逐项评价学习效果。
- 在 Tijian 接口稳定后再扩大模拟赛、排行榜、自动推荐能力。

### 建议共同确认的五项协议

1. **MCP 最小业务清单**：题面、题目状态读写、训练记录、已有成绩能否读写；同时明确错误处理。
2. **做题状态语义**：口胡/题解/代码 AC 如何区分、信息来源是用户还是 OJ/Tijian。
3. **唤醒事件语义**：绝对时刻、取消/修改、过期重放、执行状态、互斥与恢复。
4. **会话恢复策略**：自动唤醒时续聊或新聊、跨天未完结任务如何加载精确信息。
5. **文档隔离与版本机制**：Tijian MCP 说明的单文件替换目标如何测试、旧接口如何显式失败。

## 13. 下一次对话可直接使用的项目概述

> 我们要实现一个面向 OI 学习的独立 AI 教练 Skill，运行在用户现有的 Coding Agent 内，初期优先适配 OMP，也计划支持其他可配置命令行的 Agent。教练的基础能力是训练安排和做题/模拟赛分析：读取用户 TODO、作息、题目及做题状态，制定包含休息和预计思考时间的计划；接收途中反馈并动态调整；区分口胡、看题解、编码和 AC，判断学习是否有效。OI 题面和做题数据优先通过 Tijian MCP 提供，Tijian 负责其接口与独立业务文档，教练策略不直接耦合具体 MCP 调用。自动唤醒由教练项目自己的小型启动器负责，以用户可配置 Agent 命令、待执行队列和锁实现串行跟进。记忆初步按当前上下文、可编辑的长期记忆、可检索历史会话三层理解，优先评估 Agent/插件生态，不预设每日必须新开会话。系统知识拆为好题标准、CNOI 介绍、Tijian MCP 使用说明等模块，用户可另装人话题解、思考路径、Manim 和造题 Skill。需要进一步定案的是 Tijian MCP 首版接口、Tijian 内置任务队列职责、唤醒调度语义、会话恢复与跨设备同步，以及首版真实的验收范围。
